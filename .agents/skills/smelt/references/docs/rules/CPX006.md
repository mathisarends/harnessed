# CPX006 complexity/excess-comprehension-loops

A comprehension combines too many iteration or decision steps.

- **Category:** complexity
- **Activation:** explicit — Enable by rule setting or --select.
- **Severity when active:** hint
- **Automatic fix:** none; repair by hand
- **Guide:** Keep comprehensions to the configured number of for/if steps; write a loop otherwise

## Why

This opt-in syntax review reports comprehensions with too many for clauses, a conditional element/value with a nontrivial branch, or multiple filters (including a boolean filter with more than two operands). Names, attribute reads and constants are trivial branches. Nested comprehension triggers are grouped at the outermost comprehension. Simple mapping, a single filter and trivial fallbacks remain valid. Only production source is checked; no types or runtime costs are inferred.

## Bad

```python
values = [convert(x) if x.ready else fallback(x) for x in items]
```

## Good

```python
values = [resolve_item(x) for x in items]
```

## How to fix

Name the per-item decision or use an explicit loop. Preserve generator laziness, iteration/filter order and conditional evaluation. No automatic rewrite is performed. Enable rules: {complexity/excess-comprehension-loops: hint} or select CPX006; set max on the entry, e.g. {severity: hint, max: 2}. The limit defaults to 1; an entry in a style override's rules can permit intentional flattening.

## Config

- `rules`
- `style.overrides`

Explain it in the terminal with `smelt explain CPX006`.
