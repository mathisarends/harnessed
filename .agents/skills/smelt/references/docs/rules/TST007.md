# TST007 tests/vacuous-assertion

Every recognized outcome can disappear or pass trivially on empty input.

- **Category:** tests
- **Activation:** explicit — Enable by rule setting or --select.
- **Severity when active:** warning
- **Automatic fix:** none; repair by hand
- **Guide:** Check expected presence or the complete result, not only checks that pass on empty data

## Why

Assertions confined to a result-dependent loop never execute if the result is empty. A positive all(...) assertion also accepts an empty collection. This opt-in review aid reports tests whose entire recognized evidence has one of these shapes, including assertions inside one directly executed same-file helper. Empty iteration inside a helper or around its call remains subject to review. Literal nonempty iteration without filters, explicit empty-result comparisons and tests with an additional independent outcome check are retained. It does not prove collection cardinality, reachability or test effectiveness, and can flag intentional universal properties over empty collections. Checked inline Python subprocesses using an unshadowed sys.executable and literal or locally bound script text can provide direct top-level assert evidence. Dynamic scripts, files, optimized Python, shell commands and unchecked exits remain unknown; no analyzed code is executed.

## Bad

```python
def test_codegen():
    for name, content in generate().items():
        assert committed[name] == content
```

## Good

```python
def test_codegen():
    assert generate() == independently_loaded_committed_files()
```

## How to fix

Compare the complete result with an independent expectation, or check expected presence/cardinality before universal checks. Keep intentional empty-result cases explicit; do not add cosmetic assertions.
