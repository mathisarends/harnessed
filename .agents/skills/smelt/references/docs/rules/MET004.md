# MET004 meta/missing-rule-policy

An explicitly enabled rule is missing the policy it needs in its scope.

- **Category:** meta
- **Activation:** default — Enabled by default.
- **Severity when active:** warning
- **Automatic fix:** none; repair by hand
- **Guide:** Configure the policy that an explicitly enabled rule needs

## Why

An explicitly enabled rule can appear to enforce a convention even when its required policy does not reach the setting's scope. A rule named without any matching policy is a configuration error; this warning covers the narrower case. On full checks, it reports effective rule settings with no applicable public, min_imports_to_bundle, min_importers_to_export or import style policy for ARC007, IMP001, ARC008 or IMP003 respectively. It uses the declared policy and setting scope, independent of the number of source findings. Public and bundling contracts can govern callers across the project. An explicit public: [] is a policy. Changed, staged, and path-scoped checks skip this warning. CLI selection alone does not count as a setting.

## Bad

```yaml
style:
  overrides:
    api: {match: app.api, imports: {style: absolute}}
    jobs: {match: app.jobs, rules: {imports/forbidden-import-style: error}}
```

## Good

```yaml
style:
  overrides:
    api: {match: app.api, imports: {style: absolute}}
    jobs:
      match: app.jobs
      imports: {style: relative}
      rules: {imports/forbidden-import-style: error}
```

## How to fix

Configure the named policy for the intended scope. Remove the explicit rule setting or set it to off where the convention should not apply.

## Config

- `rules`
- `style.imports`
- `style.overrides`
- `architecture.packages`

Explain it in the terminal with `smelt explain MET004`.
