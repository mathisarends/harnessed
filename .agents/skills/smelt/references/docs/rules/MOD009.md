# MOD009 modeling/duplicate-class-name

Two modules of one package define a public class with the same name.

- **Category:** modeling
- **Activation:** explicit — Enable by rule setting or --select.
- **Severity when active:** warning
- **Automatic fix:** none; repair by hand
- **Guide:** Give public classes in one package distinct names

## Why

When two modules of the same package each define a public class called PageContent, imports, search results and review comments stop saying which one is meant, and the wrong import still type checks when the shapes are similar. This opt-in review groups public top-level classes by their nearest package, counting a package's __init__.py as part of that package, and reports every class whose name is also defined at the top level of another module there. Re-exports, private classes, nested classes, classes in separate packages and tests are not compared. Each definition gets its own finding with the other locations.

## Bad

```python
# app/observation/models.py
class PageContent:
    html: str

# app/observation/content.py
class PageContent(Options):
    markdown: str
```

## Good

```python
# app/observation/models.py
class CapturedPage:
    html: str

# app/observation/content.py
class PageRead(Options):
    markdown: str
```

## How to fix

Rename the classes after their role so each name says which one is meant, or merge them when they describe the same thing. A class that only exists as a private implementation detail can take a leading underscore. No automatic rewrite is performed. Enable rules: {modeling/duplicate-class-name: warning}, or select MOD009.

## Config

- `rules`

Explain it in the terminal with `smelt explain MOD009`.
