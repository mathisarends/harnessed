# TYP008 typing/prefer-inline-type-parameters

A generic class uses an explicit Generic[...] base on a Python 3.12+ target.

- **Category:** typing
- **Activation:** explicit — Enable by rule setting or --select.
- **Severity when active:** hint
- **Automatic fix:** some findings carry a fix
- **Guide:** Declare type parameters inline (class Box[T]:) instead of a Generic[T] base

## Why

PEP 695 puts type parameters on the class declaration and scopes them to the class. This opt-in rule reports parameterized Generic bases resolved through stable, direct module imports from typing or typing_extensions, including aliases. It uses project.python_version or the owning project's requires-python. A minimum below 3.12 or an unknown minimum leaves legacy syntax valid. Generic subclasses without an explicit Generic base, functions and type aliases are outside this check. Ruff UP046 covers similar syntax. Use this rule to apply Smelt's version and package policy.

## Bad

```python
from typing import Generic, TypeVar

T = TypeVar("T")

class Box(Generic[T]):
    value: T
```

## Good

```python
class Box[T]:
    value: T
```

## How to fix

Declare the parameters on the class, remove the Generic base and keep any other bases. Preserve parameter order, bounds and constraints, and check whether the target supports any parameter defaults. Review inferred variance, shared type variable uses and runtime introspection before migrating. A class that needs to retain explicit variance can use a reasoned Smelt suppression. check --fix --unsafe-fixes migrates classes whose parameters are module-level TypeVar, ParamSpec or TypeVarTuple declarations without variance or defaults, and removes declarations and imports nothing else uses; inferred variance can differ from the declared one. Enable rules: {typing/prefer-inline-type-parameters: hint}, or select TYP008.
